ennvault-claude-new · architecture walkthrough

How an invoice actually moves through this code

No prior context assumed. This walks the same path one document takes, start to finish, in the order the code actually runs it — then shows how what humans correct later loops back and changes future behavior.

Starting point: supervisor_main.py. It's a small always-on program that watches a folder for new, ready-to-process documents. The moment one shows up, it hands the document's ID (called a src_id) to the Orchestrator Agent and steps back — everything from here on is that agent deciding what to do next, one step at a time.

The big picture

Think of the system as one manager (the Orchestrator Agent, built on Claude) with six specialist departments it can call on, plus a rulebook it must follow. Each department is a small program called an MCP server — MCP is just a standard way for the manager to ask a department "do this for me" and get a plain answer back, the same way a phone extension lets you dial a specific office without knowing how that office is wired inside.

Two things flow along every arrow above: the manager asks a department a question ("what's this invoice's amount?"), and the department answers with data, never with a decision of its own. Every actual decision — is this confident enough, what should we do about this error, are we allowed to act without a human — is made by the rulebook, which is deliberately plain, testable code, not something the model improvises differently each time.

00Waking up

start A new document is ready

supervisor_main.py notices a new folder of page images, looks up which document it corresponds to in the database, and calls orchestrator.agent.process_document(src_id). That one function call is the entire hand-off — everything below happens inside it.

01The manager takes over

01 orchestrator/agent.py Claude decides

This opens a connection to all six departments at once (orchestrator/mcp_client.py starts each one as its own small background process) and starts a conversation with Claude. Claude is given a short brief — "get this document to a final state: submitted, on hold, or flagged" — and the full list of tools it's allowed to call. From here, Claude chooses the order; nothing is hardcoded to always happen next.

02Reading the document

02 Document-Intelligence server → routing.py

Claude calls the Document-Intelligence department to read the invoice's fields off the page images. That department doesn't just guess once — it reads the document a few times and checks how often it gets the same answer, which becomes a confidence score per field. orchestrator/routing.py then turns that score into one of three calls: confident enough to go straight through, shaky enough to double-check, or too uncertain and a human needs to look at it.

03Saving what was read

03 Invoice-DB server

Whatever was extracted gets written into the same invoice tables the existing system already uses, so the human-facing dashboards stay accurate no matter which path the document takes next.

04A second opinion before anything is submitted

04 orchestrator/verifier_agent.py plain rules first

Before Claude is allowed to submit anything to an ERP, it must run the invoice past the Verifier. This checks a short list of plain business rules — is the PO real, does the amount roughly match, do we know this supplier — and only after the rules have decided pass / flag / block does it optionally ask Claude to write a one-paragraph explanation for the audit trail. The verdict itself never depends on the model being reachable.

05Sending it to the ERP

05 Oracle-EBS server / JDE server

If the verifier passed it, Claude calls the matching ERP department to actually submit the invoice — the same REST calls the existing system already makes, just reachable as a named tool instead of buried inside a page route.

06When something goes wrong instead

06 errors.py → bandit.py → governance.py

A rejected submission or a blocked verdict is turned into a plain label first — "invalid PO," "duplicate invoice," and so on (mcp_servers/common/errors.py). For that label, orchestrator/bandit.py looks at which corrective action has worked best for this supplier, for this kind of error before, and suggests one. Then orchestrator/governance.py is the last gate: it only lets Claude actually carry out that action on its own if the confidence is high enough, the dollar amount is small enough, and this supplier/error combination has already earned that trust. Otherwise the recommendation goes to a human instead of being acted on.

07Talking to the supplier, when allowed

07 Supplier-Communication server

If the chosen action is "email the supplier" and governance approved it, this department sends that email and can later check whether the supplier replied.

08What humans do gets remembered

08 Memory / Policy server → learning/

Whenever a human confirms or corrects a decision, that gets logged as a small lesson: what the document looked like, what the AI suggested, what the human actually did. That lesson does two things going forward — it's stored so a similar future case can be looked up as an example, and it nudges the confidence numbers in orchestrator/bandit.py for that supplier and error type, so the same mistake is less likely to be repeated and a repeatedly-correct action is more likely to be trusted next time.

09Watching it get better (or not)

09 evaluation/metrics.py

On a schedule, this tallies up how often the AI has agreed with humans lately, how often an autonomous action was later reversed, and similar numbers, per supplier and error type. Those numbers are the only thing that can move a supplier from "always ask a human" toward "safe to act on its own" — nobody has to trust the system in the abstract, there's a number behind every step up.

The two kinds of tools Claude can call

It's worth being precise about one thing: not every "tool" in the diagram above is a department. Some are plain policy rules dressed up to look like a tool call, on purpose.

MCP server tools

Live in mcp_servers/. Each is its own small program, started separately, that reads or writes something real — the database, an ERP, an email inbox.

Native policy tools

Live in orchestrator/native_tools.py. These wrap the plain-Python rulebook (routing, bandit, verifier, governance) so Claude can call them the same way — but the math inside never changes based on what Claude "feels" that turn.
